# process · 过程协作经验

## P1 · PRD 阶段编号与 P1 增强必须分开记账

- **主张**：PRD 的阶段编号只承载阶段交付；P1 增强单独标记为「增强」，不得计入阶段完成度，也不得新增「阶段 4」。
- **适用**：PRD 只定义阶段 0–3、但开发中穿插了增强项（磁吸、交叉清理、顺序抽头）的项目。
- **Why**：把 3A/3B 写成阶段 3 已完成，会让接管者误判阶段 3 只剩收尾，实际兼容性、生命周期、冲突、性能、发布一项未做。
- **How**：进度文档固定两行——「阶段：已完成到 N / 未开始」与「P1 增强：已实现 / 默认开关」；CHANGELOG 条目显式标注「P1 增强」。
- **反例**：README 写「阶段 3 已完成（3A/3B）」导致兼容性与发布材料被忽略。
- **事实源**：DEC-020；`docs/agents/project-progress.md` 2026-11-06 状态行；提交 `8614a8a`、`b6dab5c`、`603a1b5`。

## P2 · 文档里的测试数与参数只能来自实跑或源码常量

- **主张**：测试数、间距、阈值、默认值只能写实跑输出或源码常量，旧文档不得沿用。
- **适用**：任何 README / CHANGELOG / 进度文档；尤其是迭代快、参数经常调的项目。
- **Why**：单测从 17 增至 95、lane pitch 从 5 改为 8、Ribbon 已移除，但文档三处仍写旧值，外部读者会据此判断错误。
- **How**：写前实跑 `node --test tests/unit/*.test.mjs` 取通过数；参数搜源码常量（如 `DEFAULT_LANE_PITCH`）；每次文档改动在 `agents-changelog.md` 留「旧值 → 处置 → 去处」。
- **反例**：照抄旧 CHANGELOG 的「17 项测试 / 5px 间距 / Ribbon 平行股道」。
- **事实源**：2026-11-06 实跑 95/95；`luowen/web/routing/laneAssign.js` `DEFAULT_LANE_PITCH = 8`；`luowen/web/index.js` 设置项。

## P3 · 文档与代码冲突时先列清单再改，不做静默择一

- **主张**：发现冲突先输出「冲突项 / 判定依据 / 改哪一边」，再落笔；不得只挑一边悄悄改掉。
- **适用**：接手的项目存在多份口径文档（PRD、进度、README、CHANGELOG）。
- **Why**：静默择一会丢掉另一半事实，后续会话无法判断哪边是当前真值。
- **How**：以代码与 git 历史为事实源；PRD 只作产品边界依据；把冲突项列入交付报告的「偏差清单」，已消除/仍剩余分栏列出。
- **反例**：直接按记忆把 README 改「开发尚未开始」为「已发布」，不经 git 核对。
- **事实源**：DEC-020 决策第 4 条；2026-11-06 文档对齐轮次。

## P4 · 兼容性结论必须写明取证层级

- **主张**：每条兼容性或冲突结论都要标「源码级 / 合成写入 / 运行时实测」；源码级只能说明静态冲突，不能写成「已兼容」。
- **适用**：扩展、插件、补丁类项目回答「与第三方能否共存」；尤其宿主环境被锁定、不允许安装依赖时。
- **Why**：源码级分析能看到挂载点、API 覆盖与写入位重叠，但看不到加载顺序、运行时改写时序与保存路径；把两者混写会让接管者误以为验证已完成。
- **How**：按「无交集 / 可能冲突 / 确定冲突」分档并逐条标注取证层级与 `file:line`；运行时验证方案单独成节，安装前需用户批准；矩阵顶部固定写「全部未做运行时验证」。
- **反例**：源码里看到 Zip Ties 重绘分段就下结论「共存失败」，或看到挂载点不同就写「完全兼容」。
- **事实源**：`docs/agents/compatibility-matrix.md` §5.4（19 条：8 / 8 / 3）；DEC-036；提交 `5146c82`。

## P5 · 性能优化先量后改，同页面 A/B，几何不变要逐点对比

- **主张**：性能改动必须先有基线、明确热点排序与单页 A/B；宣称「不改几何」时必须给出优化前后折线逐点一致的证据。
- **适用**：渲染/布局热路径优化，验收同时看效果与性能。
- **Why**：没有基线的「优化」无法判断收益，也无法发现退化；跨页面或跨环境比较会把布局差异误算成性能差异。
- **How**：同一宿主、同一页面、同一布局跑 A/B；记录帧时分布、求解次数、缓存命中率；数据与复现脚本入口写入性能台账；未达阈值时如实写「未达标」。
- **反例**：只报「快了 40%」不给基线，或换布局后对比两个绝对值。
- **事实源**：`docs/agents/performance.md` A/B 数据（chamfer 预筛后 500 节点 ortho 131.09ms）；DEC-035；提交 `9f93d3c`、`8d55a0b`。

## P6 · 数据不变性自检要覆盖可序列化的扩展位

- **主张**：自检快照必须覆盖工作流可序列化的所有扩展位（`graph.extra`、`node.properties`），并显式排除宿主自有键；用户态变化（坐标）只报告、不判失败。
- **适用**：声明「不改工作流数据」的渲染/交互扩展，需向用户证明不写图。
- **Why**：只比节点与链路元组时，第三方或插件写 `extra` / `properties` 完全不可见，`verify()` 会给出假阳性；把坐标算进失败又会被用户拖动误报。
- **How**：键级 diff + 深排序规范化；维护宿主自有键白名单并在测试中验证「宿主键写入仍 ok」；位置变化单列 `moved`；用合成写入 A/B 证明修前盲、修后可见。
- **反例**：`verify()` 只比 `nodeCount + link 元组`，第三方写 `extra.zipTies` 仍报 `ok:true`。
- **事实源**：BUG-007；DEC-034；提交 `ebbc038`。

## P7 · 真实鼠标验收的两个硬口径：坐标反演式与 undo 自动 rebase

- **主张**：① Playwright 真实鼠标打链路/画布目标时，图→屏换算必须用被测代码自己的反演式（本项目为 `client=(graph+ds.offset)·scale+rect`，即 `eventGraphPoint` 的逆），不能用 `graph·scale+offset`（仅 scale=1 凑巧成立）；② 宿主撤销（Ctrl+Z）经 `loadGraphData` 会触发扩展的 `afterConfigureGraph`，`verify()` 基线自动跟随撤销后状态，undo 后的 ok 不能当「与最初基线一致」的证据。
- **适用**：任何 ComfyUI 前端扩展的自动化验收；凡宿主有「撤销=整图重载」机制且扩展在加载时重建基线/缓存的场景。
- **Why**：本轮两次右键落到节点菜单、一次验收 FINAL 建立在复活节点上，都是这两个口径没对齐——前者把 hover/命中测成了 miss（假阴性），后者把污染终态判成 ok（假阳性）。
- **How**：先读被测代码的坐标换算函数再写脚本，换算式与它逐项对偶；hover 引导取点（移动→读 `status().hover`→命中再右键），不盲点坐标；涉及粘贴/删除/undo 的脚本终态做孤儿清扫 + 强制 `rebase()`；undo 复活已删对象视为正常语义，记入口径而非当缺陷。
- **反例**：`mid*scale+offset` 在 scale=0.9 的页面上偏 40px，右键弹出节点菜单还以为「菜单未注入」；删线后 Ctrl+Z 撤销的是上一步「删除粘贴件」，终态多出孤儿节点却报 ok。
- **事实源**：`renderLinkAdapter.js:1130-1136`（eventGraphPoint）；`index.js:333-336`（afterConfigureGraph 重建基线）；`.verify/p3/stage3-remaining.mjs` 与 `stage3r-run1..3.json`；debug-log BUG-006/BUG-007「真实鼠标删除复测」小节。
